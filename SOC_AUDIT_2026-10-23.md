# SOC Audit — aegis-hardened-base (image `a7ad893c7f87`, 2026-10-23)

Scope: Python 3.13.17 + Node.js 22.23.4 on `gcr.io/distroless/cc-debian12:nonroot`.
Scanners: Trivy 0.76 (vuln/secret/misconfig/license), Grype, Syft, Dockle 0.4.15, Hadolint 2.15.1,
plus in-container filesystem probes executed as UID 65532.

## 1. Verdict

**Conditionally fit for BFSI / HIPAA delivery.** The image passes every automated gate
(Trivy, Grype, Dockle, Hadolint: exit 0) with **no fixable CVE at any severity**. It carries
**43 unfixable OS-layer findings** inherited from Debian 12 that must be carried in the
risk register below, plus one unfixable HIGH in OpenSSL. Those findings are the honest
answer to "why can this not simply be declared zero-CVE".

## 2. What the previous build hid (pre-audit state)

| # | Finding | Severity | Why a regulator would reject it |
|---|---|---|---|
| 1 | "0 CVEs" was true only under `--ignore-unfixed` and a hand-written Grype ignore list. ## 3. Remediation applied this build

- **New `os-patch` stage** installs current Debian security releases of `libssl3`,
  `ca-certificates`, `tzdata` and overlays files **and dpkg metadata**. Runtime OpenSSL is
  now 3.0.22 (verified via `ssl.OPENSSL_VERSION`); scanners read the true version.
  Trivy fixable count: **8 → 0**.
- Runtime trees root-owned `0755`; probe confirms UID 65532 can write nothing outside `/tmp`.
- `npm`/`npx`/`corepack`/`node_modules` removed. SBOM: 144 npm components → **0**.
- `USER 65532:65532`; `/var/local` SGID cleared; probe confirms zero SUID/SGID files.
- `seccomp-profile.json` (Docker default minus `ptrace`, `bpf`, `mount*`, `setns`,
  `unshare`, `perf_event_open`, `process_vm_*`, `personality`, `kcmp`) + `apparmor:docker-default`.
  Python (ssl, sqlite, threads, asyncio, subprocess) and Node (crypto, https) verified under it
  with `--cap-drop ALL --read-only`.
- `make scan` now gates on Hadolint + Dockle + Trivy + Grype; new `make audit` prints
  everything unsuppressed. SECURITY.md rewritten to match the artefact.

## 4. Residual risk (cannot be removed by this image)

| Component | Count | Highest | Status |
|---|---|---|---|
| libssl3 3.0.22 | 7 | HIGH (CVE-2026-84782) | No fix in any OpenSSL 3.0 release |
| libc6 2.36 | 23 | MEDIUM | Debian `will_not_fix` / `fix_deferred` |
| gcc-12 runtime libs | 3 ×4 pkgs | MEDIUM | Debian `will_not_fix` |
| CPython 3.13.17 | 2 | MEDIUM | Fixed only in 3.15 pre-releases |

Exploitability from this image's position: non-root, zero capabilities, seccomp + AppArmor,
read-only rootfs, no shell, no package manager, no SUID. None of the residual CVEs provides a
privilege boundary crossing from that position. They remain **reportable** and must appear
in the customer's risk register with the exit conditions in SECURITY.md.

## 5. Conditions for regulated use

1. Deploy only with the compose/K8s controls shipped here (seccomp, AppArmor, cap-drop,
   read-only, numeric non-root). The image alone does not secure the kernel; nothing can.
2. Rebuild weekly: the `os-patch` stage picks up Debian fixes automatically; Python/Node
   bumps are manual (checksums in Dockerfile ARGs).
3. Sign with cosign before push; verify before pull. **Not yet done** — no `cosign.key` exists.
4. Carry Section 4 in the engagement risk register; re-evaluate on each rebuild.
5. Strategic option to retire most of Section 4: rebase the final stage on a Debian 13
   distroless when Google publishes it, or on a daily-rebuilt zero-CVE-SLA base
   (e.g. Chainguard `glibc-dynamic`), accepting a non-Debian userland.
